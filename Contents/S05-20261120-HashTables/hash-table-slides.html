CPU / HASH TABLES Git 与内容寻址

Git 怎样标识一次提交？

在有提交记录的仓库里运行第一条命令。找到 commit 后面那串十六进制字符，它就是这次提交的标识符（Commit ID）。 

git log -1 --format=fuller
git cat-file -p HEAD
这串字符从哪来？
第二条命令展示提交对象的内容，包括文件快照的引用、父提交引用（如有）、作者、提交者、时间和提交说明。Git 对编码后的对象求哈希，得到这个 ID。
怎样找回提交？
把第二条命令中的 HEAD 换成刚看到的 ID，就能读回同一个提交对象。如果只改提交说明，重新计算的 ID 通常也会改变。

CPU / HASH TABLES 从哈希值到哈希表

什么是哈希表？

哈希表（Hash Table，又称散列表）是一种根据键（Key）直接计算存储位置、从而快速存取数据的数据结构。

任意 Key ("alice")　─[ 换算下标 ]→　候选位置 i　─[ 核对 Key ]→　Value (92)
底层数组（桶 / 槽位）
长度为 m、下标从 0 到 m − 1 的连续空间，用来实际存放键值对记录。
哈希函数
把任意可哈希的键转换为整数哈希值，再压缩为合法的数组下标。
冲突处理机制
当两个不同的键算出了同一个下标时，约定它们的存放与查找规则。
CPU / HASH TABLES 从哈希值到哈希表

哈希表把查找缩小到候选位置

Key　→　H(Key)　→　H(Key) % m　→　桶或槽位
取余压缩（% m）
将哈希值 H(Key) 除以表长 m 取余，把结果限制在 0 到 m − 1 的数组下标范围内。
核对候选位置
不同键可能落入同一个位置，因此每条记录仍需保存 Key，到达候选位置后要先比对键是否相等。

CPU / HASH TABLES 字符串哈希

怎样让字符的位置影响结果？

直接相加时，cat 与 act 的字符编码之和相等。逐字符乘上底数 B，较早读入的字符就有更高的位权。

h ← h × B + ASCII(c)
初值
令 h = 0，从左向右扫描。三个字符的结果为 c₀ × B² + c₁ × B + c₂。
参数
本例取 B = 31，也可以试 131。最后用 H(s) % m 计算桶下标。

ASCII(c) 是字符的标准数字编码，例如 'A' 为 65，'a' 为 97（后续字母依次加 1）。

CPU / HASH TABLES 字符串哈希

读入字符 递推计算 当前 h
c 0 × 31 + 99 99
a 99 × 31 + 97 3166
t 3166 × 31 + 116 98262
98262 % 7 = 3　→　到桶 3 比较 Key

交换前两个字符，H(act) = (97 × 31 + 99) × 31 + 116 = 96402。

处理哈希冲突的三种方法

表长为 11，键 22 和 33 除以 11 余数都是 0。先放入 22，再来的 33 放哪？工程上分“桶内挂链”与“开放寻址”两条路线：

拉链法（桶内挂链）
留在同一个桶。把 33 接到桶 0 的链上，查找时沿链比较键。
线性探测（开放寻址）
在数组里逐格找。槽 0 已占用，就查看槽 1，若仍被占用，再查看槽 2。
双哈希（开放寻址）
在数组里按键决定的步长找。若第二个哈希函数给 33 的步长为 2，就依次查看槽 0、2、4，直到找到空槽。

CPU / HASH TABLES 冲突处理 · 双哈希

让键决定下一跳的距离

h(k, i) = (h₁(k) + i × h₂(k)) % m

第一个哈希函数，决定 i = 0 时的初始槽位（如 k % m），表长 m 决定绕回的位置。

CPU / HASH TABLES 步长与互质

一个周期能访问多少个槽位？

可访问槽位数 = m / gcd(m, step)
表长 12，步长 8
gcd(12, 8) = 4，只能访问 0 → 8 → 4，第四次又回到 0。
表长 11，步长 3
gcd(11, 3) = 1。从槽 2 出发，依次经过 5、8、0、3、6、9、1、4、7、10，再回到 2。
选择步长
让有效步长落在 1 到 m − 1，并与表长互质。这样重复前恰好能检查全部 m 个槽位。

CPU / HASH TABLES 容量与性能

装载因子衡量表有多满

α = n / m　　　4 条记录 / 11 个槽位 ≈ 0.36
拉链法
α 表示平均链长，一个桶能存多条记录，因此 α 可以大于 1。
开放寻址
每个槽位最多一条有效记录，α ≤ 1。空槽减少或 DEL 累积，通常都会延长探测。
何时扩容
例如开放寻址可在 α 约为 0.7 时扩容。实际阈值由实现和工作负载决定。
CPU / HASH TABLES 容量与性能

表长变了，22 应该搬到哪里？

22 % 11 = 0 → 22 % 23 = 22　｜　33 % 11 = 0 → 33 % 23 = 10
分配
创建更大的空表，本例从 11 个槽扩到 23 个槽。
重算
用新表长计算每个有效键的起点，双哈希还需确保步长与新表长互质。
重插
按新的探测规则逐条插入有效记录，旧表的 DEL 可以丢弃。这个过程称为 rehash。

期望 O(1) 有哪些前提？

情形 时间成本 成立条件或原因
查找 期望 O(1) 分布均匀、装载合理，键哈希和比较按常数计
插入 期望摊还 O(1) 按比例扩容，迁移开销分摊到多次插入
一次扩容 通常 O(n) 需要重新插入 n 条有效记录
极端碰撞 最坏 O(n) 查找可能检查一整条长链或探测路径

若键是长度 L 的字符串，首次逐字符计算哈希还需 O(L)。

CPU / HASH TABLES 标准库

什么样的对象适合当键？

k₁ == k₂　 ⇒　 hash(k₁) == hash(k₂)
稳定性
键在表内期间，参与哈希和相等比较的状态应保持稳定。Python 的 str、int 和元素均可哈希的 tuple 可以作键，list 不可哈希。
自定义对象
C++ 为键提供相容的哈希函数和相等比较。Java 自定义 equals() 时应同时实现相容的 hashCode()。
遍历顺序
插入顺序与按键排序是两种语义。需要按键有序遍历时，可用 C++ std::map 或 Java TreeMap。
